# Лабораторная работа № 2

Разработка SQL-запросов и аналитических сценариев. Предметная область та же, что в ЛР 1:
учёт студентов, групп, преподавателей, курсов и результатов экзаменов.

## Порядок запуска

База `lab1` должна уже содержать схему и данные из ЛР 1 (`lab1/schema.sql`, `lab1/data.sql`).
Скрипты выполняются **один раз, строго по порядку**:

```bash
sudo systemctl start postgresql
cd lab2
psql -U postgres -h localhost -d lab1 -f 0_migration.sql
psql -U postgres -h localhost -d lab1 -f 1_1_data.sql
psql -U postgres -h localhost -d lab1 -f 1_2_dml.sql
psql -U postgres -h localhost -d lab1 -f 2_1_joins.sql
psql -U postgres -h localhost -d lab1 -f 2_2_aggregation.sql
psql -U postgres -h localhost -d lab1 -f 3_subqueries.sql
psql -U postgres -h localhost -d lab1 -f 4_cte_report.sql
```

`2_1`–`4` только читают данные, их можно запускать сколько угодно раз.
`0`, `1_1` и `1_2` изменяют базу. Чтобы начать заново, пересоздайте базу:

```bash
psql -U postgres -h localhost -c "DROP DATABASE lab1" -c "CREATE DATABASE lab1"
psql -U postgres -h localhost -d lab1 -f ../lab1/schema.sql
psql -U postgres -h localhost -d lab1 -f ../lab1/data.sql
```

## Расширение модели (0_migration.sql)

В ЛР 1 в `exam_results` можно было записать только выставленную оценку, поэтому
у бизнес-процесса «экзамен» не было состояний. Добавлено поле `status`:

| status | смысл | grade |
|---|---|---|
| `scheduled` | экзамен назначен, ещё не состоялся | NULL |
| `completed` | экзамен состоялся, оценка выставлена (2 = «неуд») | 2–5 |
| `absent` | неявка | NULL |
| `cancelled` | попытка отменена или перенесена | NULL |

- `grade` теперь может быть NULL. Новый CHECK `(status = 'completed') = (grade IS NOT NULL)`
  требует, чтобы оценка была тогда и только тогда, когда экзамен состоялся.
- Старые строки получают `status = 'completed'` через DEFAULT, поэтому данные ЛР 1 сохраняются.
- Первичный ключ `(student_id, course_id, exam_date)` уже позволял хранить несколько попыток
  одного студента по одному курсу (пересдачи), это используется в данных.

## 1.1. Данные (1_1_data.sql)

После всех скриптов в базе: 5 групп, 28 студентов, 5 преподавателей, 9 курсов,
122 записи в `exam_results`, всего около 170 записей.

Выполнение требований:

- **≥ 100 записей, ≥ 30 в одной таблице:** 122 записи в `exam_results`.
- **≥ 3 состояний процесса:** `scheduled`, `completed`, `absent`, `cancelled`.
- **≥ 3 месяцев:** декабрь 2025 (досрочная сдача), январь 2026 (сессия), февраль–март 2026
  (пересдачи), июнь 2026 (летняя сессия), сентябрь 2026 (пересдачи), ноябрь 2026 – январь 2027
  (назначенные экзамены).
- **Повторяющиеся операции:** пересдачи. Например, Козлов сдавал АиСД три раза (2 → 2 → 3),
  Семёнов не может сдать матанализ (2 → 2 → неявка).
- **Сущности без операций:** группа ПМИ-108 и её студенты (первокурсники, сессии ещё не было),
  Лебедева (переведена), преподаватель Волкова (не ведёт курсов), курс «Машинное обучение»
  (экзаменов не было).
- **Пограничные значения и NULL:** оценки 2 и 5 (границы CHECK), курс «Философия» с 1 кредитом
  и без преподавателя (`professor_id = NULL`), `grade = NULL` у несостоявшихся попыток,
  группа ПМИ-108 с нулевыми показателями.

Связи в INSERT ищутся по естественным ключам (`email`, `course_name`, `group_name`), а не по id.
После неудачных INSERT из `constraints_test.sql` счётчики SERIAL сдвигаются, поэтому
жёстко заданные id могли бы указать не на ту строку.

## 1.2. DML (1_2_dml.sql)

1. **INSERT:** новый студент Смирнов переведён в ПМИ-307, и ему сразу назначены два экзамена.
   Сначала INSERT студента, потом INSERT двух экзаменов. id студента берётся подзапросом по email.
2. **UPDATE состояния:** экзамен Смирнова по БД переходит из `scheduled` в `completed` с оценкой 4.
3. **Массовый UPDATE:** все запланированные экзамены по курсам преподавателя Кузнецовой
   переносятся на неделю (`exam_date + INTERVAL '7' DAY`). Курсы Кузнецовой отбираются
   подзапросом в `WHERE course_id IN (...)`, изменяются 3 строки.
4. **DELETE:** удаляется ошибочно назначенный Смирнову экзамен по ОС.
   Шаги 1–4 выполняются в одной транзакции и завершаются `COMMIT`.
5. **ROLLBACK:** в отдельной транзакции удаляются студент Баранов и преподаватель Соколов.
   На этом показаны ограничения целостности:
   - `ON DELETE CASCADE`: вместе с Барановым удаляются его 6 результатов (122 → 116);
   - `ON DELETE SET NULL`: курсы Соколова остаются без преподавателя (1 → 3 курса с NULL).

   После `ROLLBACK` счётчики возвращаются к 28 / 122 / 1.

## 2.1. JOIN (2_1_joins.sql)

1. **Подробная информация:** ведомость зимней сессии. Соединяются 5 таблиц.
   Для преподавателей используется `LEFT JOIN`, иначе выпали бы экзамены по «Философии»,
   у которой нет преподавателя. `COALESCE` выводит вместо NULL текст «не назначен».
2. **Объекты без связанных записей:** студенты без единого экзамена, через `LEFT JOIN ... WHERE er.student_id IS NULL`.
   Результат: 3 студента ПМИ-108 и Лебедева.
3. **Несколько условий:** студенты набора 2024 года, получившие «отлично» в летнюю сессию
   по курсам кафедры ВМиП.

## 2.2. Агрегация (2_2_aggregation.sql)

Используются агрегаты COUNT, SUM, AVG, MIN, MAX.

1. **Количественные показатели по группам:** число студентов, сданных экзаменов, неявок, двоек и
   назначенных экзаменов. Каждый счётчик — `SUM(CASE WHEN условие THEN 1 ELSE 0 END)`. `LEFT JOIN` нужен, чтобы
   ПМИ-108 попала в результат с нулями.
2. **HAVING:** «проблемные» курсы со средним баллом ниже 4, по которым было не меньше 5 экзаменов.
3. **Сравнение периодов:** показатели по месяцам (`GROUP BY EXTRACT(YEAR ...), EXTRACT(MONTH ...)`).
   Хуже всего февраль (пересдачи): средний балл 3,08 и 37,5 % неудачных попыток. Лучше всего декабрь
   (досрочная сдача): средний балл 4,27.

## Часть 3. Подзапросы (3_subqueries.sql)

- **3.1:** студенты, у которых средний балл выше среднего по их группе.
  Средний балл студента считается через `GROUP BY`, а средний балл группы — подзапросом в `HAVING`.
- **3.2 EXISTS:** «двойки», которые студент потом пересдал. Условие: существует более поздняя
  запись по тому же курсу с оценкой ≥ 3.
- **3.3 NOT EXISTS:** текущие академические задолженности. Студент уже пытался сдать курс
  (получил 2 или не явился), но записи с оценкой ≥ 3 по этому курсу нет.
  Отсутствие события «курс сдан» здесь означает долг, который нужно закрыть.
  Курсы, где есть только `scheduled`, долгом не считаются, потому что экзамен ещё не наступил.
- **3.4 Коррелированный подзапрос:** для каждого студента вычисляются число попыток, средний балл,
  число сданных курсов и дата ближайшего экзамена. Каждый подзапрос в SELECT зависит от
  `s.student_id` текущей строки внешнего запроса.

## Часть 4. Отчёт на CTE (4_cte_report.sql)

**Вопрос замдекана:** как каждая группа прошла сессии 2025/26 учебного года? Каков средний
итоговый балл, сколько студентов сдали всё с первого раза и сколько осталось должников?

**Схема вычислений:**

```
exam_results
   │  отбор состоявшихся попыток (completed/absent) за 01.09.2025–30.09.2026
   ▼
attempts                  ── исходные данные: одна строка = одна попытка
   │  GROUP BY студент, курс
   ▼
course_outcome            ── промежуточные показатели: итог по паре «студент–курс»
   │  GROUP BY студент
   ▼
student_summary           ── промежуточные показатели: итог по студенту
   │  LEFT JOIN с группами и студентами, GROUP BY группа
   ▼
group_summary             ── агрегация по группам
   │  процент, сортировка
   ▼
итоговый отчёт            ── одна строка = одна группа
```

| Этап | На входе | Преобразование | Результат |
|---|---|---|---|
| `attempts` | `exam_results` | оставить только состоявшиеся попытки учебного года, отбросить `scheduled` и `cancelled` | список попыток |
| `course_outcome` | `attempts` | группировка по (студент, курс): `COUNT` попыток, `MAX(grade)` как итоговая оценка, флаги `passed` (оценка ≥ 3) и `first_try` (сдан с одной попытки), 1 = да, 0 = нет | итог по каждому курсу каждого студента |
| `student_summary` | `course_outcome` | группировка по студенту: средний балл по сданным курсам, долги = курсов всего − сданных, `MIN(first_try)` = 1, только если все курсы сданы с первого раза | профиль студента |
| `group_summary` | `academic_groups`, `students`, `student_summary` | `LEFT JOIN`, чтобы учесть студентов и группы без экзаменов; группировка по группе | средний балл, число сдавших всё с первого раза, число должников |
| итоговый SELECT | `group_summary` | процент сдавших с первого раза (`CASE` защищает от деления на 0), сортировка по среднему баллу, группы без данных в конце (`NULLS LAST`) | отчёт |

Результат:

```
 group_name | students_total | students_examined | group_avg_grade | first_try_students | first_try_pct | debtors
------------+----------------+-------------------+-----------------+--------------------+---------------+---------
 ПМИ-307    |              7 |                 6 |            4.06 |                  4 |          66.7 |       2
 ПМИ-206    |              6 |                 6 |            3.96 |                  3 |          50.0 |       2
 ПМИ-306    |              7 |                 6 |            3.94 |                  3 |          50.0 |       1
 ПМИ-406    |              5 |                 5 |            3.93 |                  3 |          60.0 |       0
 ПМИ-108    |              3 |                 0 |                 |                  0 |               |       0
```

Вывод по данным: у ПМИ-307 лучший средний балл (4,06), но в группе 2 должника.
У ПМИ-406 немного ниже средний балл, зато нет долгов. У ПМИ-108 данных пока нет:
сессии ещё не было, и группа стоит последней.

## Возможные вопросы на защите

- **Чем LEFT JOIN отличается от INNER JOIN?** LEFT JOIN сохраняет все строки левой таблицы,
  даже если справа нет пары. Недостающие столбцы правой таблицы заполняются NULL.
- **WHERE или HAVING?** WHERE фильтрует строки до группировки, HAVING фильтрует группы после неё.
  Поэтому агрегаты можно писать только в HAVING.
- **Почему `COUNT(DISTINCT s.student_id)` в 2.2.1?** После JOIN с экзаменами каждый студент
  повторяется столько раз, сколько у него экзаменов. DISTINCT считает каждого студента один раз.
- **Как посчитать строки по условию?** `SUM(CASE WHEN условие THEN 1 ELSE 0 END)`: подходящая
  строка даёт 1, остальные 0, сумма = количество подходящих.
- **AVG и NULL:** агрегатные функции пропускают NULL, поэтому неявки не портят средний балл.
- **EXISTS vs IN:** EXISTS проверяет, есть ли хотя бы одна строка, и останавливается на первой
  найденной. NOT EXISTS, в отличие от NOT IN, корректно работает, если в подзапросе есть NULL.
- **Что такое коррелированный подзапрос?** Это подзапрос, который ссылается на столбец внешнего
  запроса. Логически он выполняется заново для каждой строки внешнего запроса.
- **Что такое CTE?** Именованный подзапрос в блоке `WITH`. Он разбивает сложный запрос на шаги
  и позволяет ссылаться на предыдущие шаги.
- **Транзакция и ROLLBACK:** `BEGIN` открывает транзакцию. Изменения в ней видны только внутри неё,
  пока не выполнен `COMMIT`. `ROLLBACK` отменяет все изменения транзакции.
